# Maintainer release

`batch-release.sh` installs a reviewed Gene main (control plane plus cogs) and then a reviewed Fri main on the host, one phase at a time. It is the daily release's tool. Run it as root:

```sh
batch-release.sh <phase> <full gene sha G> <full fri sha F>
```

It upgrades from whatever is live. Before `baseline` that is read from `release.env` (Gene) and `/srv/fri/release.env` (Fri). `baseline` checks the live pair is healthy and consistent and records it in the manifest, and every later phase uses that record. When G is already live, the release changes only Fri; when F is already live, only Gene. Both live is refused. The modes:
- **Gene and Fri.** Every phase as described below.
- **Fri only** (G live). Only `fri.tar` is uploaded. `stage` builds only the Fri image and checks it against the live controller's contract. `rehearse` has nothing to migrate. `gene` re-runs the fence and checks the old Gene, nothing more. `fri` first backs up Fri's pins and record. Red, the controller and the cogs are never touched. Roll back with `rollback-fri`, never `rollback-gene`.
- **Gene only** (F live). Only `gene.tar` is uploaded. `stage` checks the live Fri against the new contract. `fri` probes the live Fri against the new Gene and doesn't restart it.

Only one batch command runs at a time on the host: each takes `/srv/gene/batch-release.lock` (except `status`), and every command it starts inherits the lock. So if a batch shell is killed, anything it left running keeps the lock until it ends, and a rollback refuses rather than racing it. `fuser -v /srv/gene/batch-release.lock` shows the holder.

It never prints secrets: env files are passed to Docker, copied or compared, never echoed. It never starts the legacy `fri` service in Gene's compose or `gene-fri-1`.

## Maintenance window
Owner policy, 2026-10-27: production changes start only in [04:00, 05:00) America/Los_Angeles, following daylight saving, and one production batch runs per local calendar day across both routes: a batch that drains here, or one approved automatic feature or repair deployment, which counts once the controller claims it, whatever its outcome. Whichever comes first uses the day. The script checks before anything else, so a refused command takes no lock, creates no staging dir and writes nothing but its log line. It exits 4 and names the batch's safe path.
- **Inside the window only:** `baseline`, `stage`, `rehearse`, `drain`, `gene`, `fri`, `evals`, `cleanup`. `baseline`, `stage`, `rehearse` and `drain` also refuse once today's batch is used: another batch drained today, or an automatic feature or repair deployment was claimed today. Deployments come from the controller's own record, its `deployments` rows since local midnight counted as `/deploy/claim` counts them (whatever the outcome, also one whose job is gone or one dated later; rollbacks never count), plus any `deploy feature job` or `deploy repair job` line dated today in the action log. Drains come from the batches' journals, dated by the action log; a batch from before the log is dated by its journal's last change. An unreadable clock or history counts as used, and so does a missing or unreadable controller DB: the phase holds with exit 4. This check runs before anything else, so it reads the DB on the host, read-only: a read-only connection creates no journal file, and SQLite gives a shared-memory file it creates as root to the DB owner. A retry after a rollback is a new batch, so it waits a day.
- **The drain checks again after its fence,** since the fence waits out a deployment the controller claimed before the pause. If that deployment used today's batch, the drain starts the worker and deployer again, unpauses if its own pause is still the latest (see **Pause** below), and stops (exit 1) without draining: the deployment may have moved Gene, so it doesn't make `resume-old`'s old-pair check. The batch doesn't go forward again. A drained batch records a `batch_drained` audit row in the controller DB before its journal line, which holds the controller's automatic claims for the rest of the day.
- **Critical fix:** `CRITICAL_FIX='<P0 reason>'` lets a batch past the daily cap when the fix is for a crash, data loss, a privacy leak or a broken rollback. It never lifts the window. The log records it as the exception (`critical fix: <reason>`). A critical batch that drains still uses the day, so the controller holds automatic claims after it.
- **At any hour:**
  - `rollback-gene`, `rollback-fri` and `resume-old`. `resume-old` also restores service after a `drain` that paused but timed out before `drained`.
  - `status` and `verify-off`, once this batch has paused development. Each starts a throwaway read-only DB container. `verify-off` records `verified_off`.
  - `accept-evals`, once `evals` has run. With `EVALS_ACCEPTED='<why>'` it records the eval rule's decision to keep a release whose suites had failures.
  - `resume`, once the last `evals` run passed (`evaluated`, from a clean run or `accept-evals`) and `verify-off` passed (`verified_off`). Each `evals` run starts over (`evals_started`), so a failed rerun cancels an earlier pass.
- **A batch that has resumed the old release** doesn't go forward again.
- **Waits that cross 05:00:** the script checks again before each switch, image build, and every container `stage` and `rehearse` start (checks, module probes, DB copies, migrations, downgrades), before each eval suite, and after the drain's wait.
  - Before `drained` or a switch, a closed window means `drain`, `gene` and `fri` switch nothing and take the safe path themselves: `resume-old`, or `rollback-gene` then `resume-old` once Gene switched.
  - A closed window stops `evals` before its next suite. The release is rolled back and the old one resumed.
  - A closed window stops `stage` or `rehearse` before its next build or container. Production is untouched, so the phase is repeated in a later window: `stage` removes the trees an interrupted stage left (never after `staged`), and `rehearse` never leaves its DB copies.

  Each of these then exits 1.
- **Unknown clock or zone** counts as closed for forward phases: a clock before 2026-10-27, an unreadable clock, or no zone database. Recovery never reads the clock to decide, and its health probes time out on bash's `SECONDS`, so a failing `date` can't stop a rollback.
- **Exception:** `MAINTENANCE_EXCEPTION='<who, when, why>'` lets a refused phase run, outside the window or past the daily cap. Set it only on the owner's explicit words for that change. The log records it.
- **Action log:** `/srv/gene/production-actions.jsonl` (root, 0600). Each command appends one line, except `status`: local time and zone, `local_date`, actor (`SUDO_USER`), trigger (`BATCH_TRIGGER`, default `maintainer`), action, reason, staging dir, live Gene/Fri SHAs before and after, duration, the `gene`/`fri` restart time, outcome (`ok`, `failed: exit N` or `refused: …`), exception, and a `note` when development was left as someone else set it. It holds no secrets or member content. Past 1 MiB it keeps its newest half. `gene.fri_release` and the automatic deployer append to the same file.

The controller holds automatic deployments to the same window and cap. `/deploy/claim` hands out approved feature and repair jobs only in [04:00, 04:50), and only while today's batch is unused: no feature or repair deployment claimed since local midnight and no `batch_drained` audit row from a maintainer drain. An unknown clock, zone or history counts as used, and a held job stays `approved`, untouched, for a later day. An owner's rollback is claimed at any hour and never counts. A critical fix is exempt from the cap, not the window: on the owner's explicit words, mark an approved feature or repair job with `sudo -n /srv/gene/venv/bin/python -m gene.maintenance critical <job id> --reason '<P0 reason>'`. It refuses any other job and an empty reason, holds only for the commit the job was approved at, writes an audit row and a production-action log line with the reason as the exception, and keeps the mark in its own `critical_fixes` table, which an older controller ignores. `python -m gene.maintenance critical-list` shows the marks read-only. A critical deployment still uses the day if it comes first. The deployer checks again before preparing and right before the switch. If preparing ran past the close, it removes the cogs it just installed and fails the job unswitched, and the job needs approving again. `gene.fri_release` checks at start and right before stopping Fri, and refuses outside the window except for a rollback to the Fri the live one replaced or a `MAINTENANCE_EXCEPTION`. `src/gene/maintenance.py` holds the window for both.

## Before running
1. Fetch both repos. Confirm G and F are the reviewed mains, and that CI is green on both.
2. Read F's `docs/integration-pair.json` and get `verified_controller_commit`. It must be an ancestor of G.
3. Run `baseline`, which creates `/srv/gene/staging/batch-$G-$F/` (root, 0700). Upload the inputs there, for each half that changes:
   - `git archive --format=tar` of the commit, as `gene.tar` or `fri.tar`
   - `sha256sum gene.tar > gene.tar.sha256`, and the same for `fri.tar`
4. Upload the script itself to a root-owned path.

Retrying the same G and F after a rollback is a new batch, so it waits for a later day's window. It needs a fresh staging dir and result file: set `BATCH_ATTEMPT=2` (any number) on every phase, and, when the failed attempt changed Gene, move its `releases/$G` aside first. A Fri-only attempt never created `releases/$G`: that tree is the running Gene's cogs, so leave it in place. The retry stages in `batch-$G-$F-2` and writes `maintainer-$G-$F-2-result.json`.

If Gene deployed a member's request since the last maintainer release, `release.env` names that request's SHA while the runtime image and worker pin still carry the maintainer release, and `baseline` refuses (`runtime_label`, `worker_pin`). Make sure the request is in G, then reconcile by hand.

## Phases
| Phase | Member impact | What it does |
|---|---|---|
| `baseline` | none | Requires the tools it uses, a controller DB whose directory and journal files share its owner, and a healthy live pair at OLD_G / OLD_F: settings, pins, images, labels, a source tree that is unmarked or marked with the old release, fresh heartbeats with a presence, controls, connections. Records it, plus the exact running image IDs, in `baseline.json` and `manifest.json`. |
| `stage` | none | Walks a probe directory through staging, `releases/`, the source tree's parent and the backups dir by plain `rename(2)`, and refuses if any hop fails. A matching device number isn't enough, since a bind mount shares one and still refuses renames. It also reads the kernel's mount table and refuses a mount point at or under the source tree or either staged tree, since a bind mount there looks like a plain directory. Every tree move in the switch and its rollback is then a single rename that fails rather than copying. Disk admission on every filesystem it will write: Docker, staging, both backup dirs, `releases/` and the source tree. Checks the archive hashes and extracts into fresh dirs. Refuses dependency or ops diffs (`ALLOW_OPS_DIFF=1` after review). Prepares the immutable cog tree and records its hash. Builds the labelled images and records their IDs. Runs isolated import checks, the controller contract on synthetic state, a check that Fri accepts that contract, and a test of the audio player snapshot. |
| `rehearse` | none | Works out which downgrades a rollback needs and records them in the manifest: each module in `DOWNGRADE_MODULES` that G has and the old release lacks. A feature the old release already has is never downgraded, since that would delete data it reads. Both images are asked with a probe that answers yes or no, so a container that fails to start stops the phase rather than skipping a step. Then it copies the live DB twice into a private dir that is always removed. Migrates one copy with G, starts the exact rollback image on it, and writes a request with old code. Migrates the other and runs the recorded downgrades with the controller's env. For `gene.profile_downgrade` the copy holds one profile removal, so a `controller.env` without the configured channels (which the downgrade needs to keep removals) stops here instead of halfway through a rollback. Then it starts the rollback image on it. |
| `drain` | development pauses | The fence: pause (audited), wait for building/deploying work and `deploy-result.json` to clear, stop gene-worker and gene-deployer, recheck. |
| `gene` | Red ~1 min, controller seconds | Re-runs the fence, verifies the old pair and the cog, rename and disk checks, then waits until the audio node reports zero players. Players left idle in voice are a stop: ask the owner. It verifies the old pair again and writes a complete backup into a unique dir: a DB copy, Red's data, and the four pin files with their modes kept. Only then does it journal the attempt. It renames the cogs into place, takes a fresh player snapshot, stops Red, swaps the source, and pins `release.env` and the worker image. It starts controller and red, probes health against the baseline guild and presence, then records `active_sha` / `previous_sha` plus an audit row in one guarded transaction. Any failure after the attempt is journaled runs `rollback-gene`. |
| `fri` | Fri ~1 min | `gene.fri_release F` (G's coordinator), then a probe. On failure it prints the state; `rollback-gene` puts the old Fri back from any partial state. The workers stay stopped. |
| `evals` | none | Live `requests`, `sass` and `controls` suites inside `fri-runtime-1`, then Fri's heartbeat stages (failing ones by exception class) and its rejected usage receipt count. Exits nonzero if any suite failed, after reporting all of them. Never rolls back by itself: that is a call to make with the owner. |
| `verify-off` | none | Reply checks are off and have no runs. |
| `resume` | development resumes | Full consistency check: images, pins, source, records, settings, health and idle. Then starts the units, unpauses only if this release's pause is still the latest (see **Pause** below), records an audit row, and writes `/srv/gene/maintainer-G-F-result.json` (`maintainer-G-F-N-result.json` with `BATCH_ATTEMPT=N`). Safe to repeat after a crash: the result file is written in full to a temporary of its own and then linked into place, and a repeat accepts its own result. A repeat after it finished checks the new release and running units again before it says so. |
| `cleanup` | none | Removes the staged sources and tars. Removes `gene-runtime`, `gene-worker` and `fri-runtime` images tagged with a release SHA nothing recent needs, never forced, so one a container uses stays (`KEEP_IMAGES=1` skips this). It keeps this release's old and new images, the images the live `release.env` files and worker pin name (whichever release set them, so repeating an older release's cleanup is safe), and the old and new images in the manifests of the `KEEP_RELEASES` (default 3) most recently resumed releases, so a rollback that many releases deep still finds its images. It also keeps every image of a release that isn't back in service yet (staged, drained, switching or mid-rollback), however old. An older release's rollback refuses at its image check once its images are gone. Keeps the journal, manifest, baseline, evals and backups, and reports how many backups each backups dir holds: they hold member data, so removing them is the owner's call. |
| `rollback-gene` | yes | Not for a Fri-only release. Reconciles from actual state, so it is safe to repeat at any point. It first checks that every live piece is from the recorded old or new release, and refuses without changing anything otherwise. Then it fences, takes `gene.fri_release`'s lock for the rest of the run, and checks again, since the fence may have waited for a deployment that landed a third release. Then: put the old Fri back, stop the new containers and run the downgrades `rehearse` recorded with G's image, restore pins and source, start the exact old images, probe Gene, reverse the settings (a no-op if already old), probe Fri, verify. It never restores a DB snapshot; that stays an operator decision. Once it has started, `gene`, `fri` and `resume` refuse: a rollback that was interrupted is finished by repeating it, then `resume-old`. |
| `rollback-fri` | Fri ~1 min | Fri-only releases. Reconciles from actual state, so it is safe to repeat, through the backup of Fri's pins and record the `fri` phase took before its first attempt (a retry never retakes it). It refuses without changes unless live Fri is from the recorded old or new release and Gene is still exactly G (settings, `release.env`, worker pin, source and images: a member request deployed since means the old pair no longer exists, so reconcile by hand). It fences, takes `gene.fri_release`'s lock and checks both again; if Gene moved during the fence it starts the worker and deployer again, unpauses if its own pause is still the latest, and stops with Fri untouched. Then it puts the old Fri back as `rollback-gene` does, probes it and verifies the old pair. After a `fri` phase that failed and recovered by itself, `resume-old` alone is enough: it verifies the old pair first. |
| `resume-old` | development resumes | After a rollback once the old pair verifies, or after a `gene` phase that stopped before switching. |
| `status` | none | Read-only state plus the journal. |

## How it touches state
- **Controller DB.** Every read and write runs as the DB's owner in a throwaway container of the old runtime image, with only the data dir mounted, except the daily cap's read-only check (see **Maintenance window**). So no root SQLite client leaves journal files the controller can't open, and pausing, recording and checking work while the controller is down. `gene.fri_release` and `gene.maintenance critical` still open the DB as root. SQLite normally hands new journal files to the DB owner anyway, but every DB access first gives back any it didn't, so a crash in the middle of a Fri release can't lock the helpers out. The diagnostics go to stderr, so captured output stays clean. The read-only `baseline` and `status` only report them. Every state read that decides something, such as whether to take the pause, has to succeed.
- **Pause.** The journal line `intent:pause` is written before pausing. The pause checks, in its own transaction, that development is still unpaused: if someone paused it after the fence looked, the batch journals `skipped:pause` and takes no pause. The pause's audit row names the batch (its staging dir), and its id goes in the journal (`paused:<id>`). `resume`, `resume-old`, the drain's stop after the fence and `rollback-fri`'s stop unpause only while the journal's latest pause is this release's and that audit row is still the controller's latest pause or resume, checked and changed in one transaction. A pause killed before its id reached the journal is known by the batch its row names. A pause the script made before audit ids (`8deef14`) names no batch and has no id in the journal; it counts as the batch's own when it is by `maintainer:claude` and no older than the batch's `baseline.json`. So a pause the owner made through `/pause` during the batch stays, and so does a resume they made; the log, the action-log line's `note` and the exit message say so. A pause someone set before the release stays too.
- **Fri on rollback.** The rollback holds `gene.fri_release`'s lock before it looks at Fri, so a coordinator that outlived a killed batch shell makes it stop instead of racing it. If the old Fri's pins, record and image are not all in place, it works through the switch backup. It restores `release.env` and `release.json` byte for byte, sets `fri_active_sha` with an audit row, and starts the old runtime. This covers a clean new Fri and an interrupted Fri release alike, and needs no healthy controller. Fri's health is probed once Gene is back.

## Compatibility boundary
A rollback never restores a DB snapshot: the old release runs on the migrated DB, after the downgrades for features it lacks. `rehearse` starts the old image on a migrated copy and writes with it, so a schema change it can't run on stops there. Data it would run on but misread is the feature's job: a Gene change whose data an older release would handle wrongly (dropping a privacy removal, say) ships a downgrade module, and gets an entry in `DOWNGRADE_MODULES` and `downgrade_step`. The ones so far, all added after `f667001`:
- `gene.fri_reply_checks purge` drops the reply-check tables and settings.
- `gene.profile_downgrade` deletes member-profile notes, copies their removals to every configured and known channel, and keeps conversation notes and exchanges. It never migrates, and it reads the channels from `FRI_CHANNEL_IDS` and `FRI_HISTORY_CHANNEL_IDS` in `controller.env`.
- `gene.fri_member_summary purge` drops Fri's member summaries and their daily call stamps, since an older controller could neither show, edit nor erase them.

`7d6e36a` has the first two features, so a rollback to it runs only the member-summary purge. Don't run `gene.provenance_downgrade` either: every release since `f667001` has turn provenance, and it would discard member continuity they support.

## Offline tests
`FRI_REPO=<fri checkout> ops/maintainer/test/run.sh [t_name ...]` runs the script against mock hosts: stub docker, systemctl and curl, and a controller DB created by the old code as uid 10001. Each `docker run` executes the real command with the image's code: an export of OLD_G, this checkout for G, and FRI_REPO for F. The live release defaults to `f667001`; tests set `MOCK_OLD_G` / `MOCK_OLD_F` for others. It runs as the requested user and refuses anything it does not model. Every phase's exit code and the resulting state are asserted. Scenarios:
- the full release, with a failing eval suite, then repeats of resume and cleanup
- a failed health check with auto-rollback, a repeated rollback, then resume-old
- players on the audio node for the whole window: no switch, then resume-old
- the maintenance window: refusals outside it with no lock, staging or journal; the daylight-saving day; a drain, a Gene fence and a Fri-only fence whose waits cross 05:00 and resume the old release themselves; a drain that timed out after pausing, resumed after 05:00; a build, a check container and an eval suite cut off by the close; a failed eval rerun cancelling an earlier pass; a rollback with no readable clock; switched halves found after 05:00 rolled back at once; a passing release, and one kept by `accept-evals`, resumed after 05:00 once `verify-off` passed; one batch a day, the owner's exception, and the next day's retry; an automatic deployment that finishes during the drain's fence, which resumes development without draining, then a same-day retry refused until `CRITICAL_FIX`, whose drain is logged and leaves the controller's `batch_drained` hold; the same deployment recorded only in the controller DB, with no action-log line, which also stops the drain and refuses that day's retry. A fake `date` shifts only the window's clock (`TZ=UTC date +%s`); `tests/test_maintenance.py` covers the exact boundaries with a stopped clock.
- a player appearing mid-switch
- a failed Fri release that recovers itself, then rollback
- an interrupted Fri release, reconciled by rollback
- a rollback after resume, after a member removed a profile note, whose removal the downgrade keeps in the configured channel
- a controller env without the configured channels, which the rehearsal refuses
- a downgrade probe that fails to run, which stops the rehearsal rather than skipping a downgrade; the rollback then runs the recorded list without probing
- a rollback after resume with the controller down
- a crash right after a mutation, then rollback
- a rollback killed after it stops the new Gene, where resume refuses and a repeated rollback finishes
- a live state outside the recorded pair, which rollback refuses without changes
- a deployment that lands a third release while the rollback fence waits, refused before Fri or Gene is touched
- a Fri coordinator still holding its lock, which rollback waits out
- backups moved to another filesystem, refused before the switch
- backups bind-mounted on the same filesystem (same device number, renames refused), refused before the switch
- the source tree bind-mounted onto itself, refused before the switch with Red still running
- a killed batch shell whose Gene compose up keeps running, which rollback waits out
- an owner's pause from before the release, with root-owned journal files at drain, which the release leaves in place
- an owner's pause made during the batch, which stays: during the drain's fence, before `resume-old`, and before `resume` after a full release
- an owner's pause between the fence's read of the setting and the batch's pause, which the batch never takes for its own
- a batch drained by the script from before pause audit ids (`8deef14`) and finished by this one: `resume-old`, `resume` after a full release, and `rollback-fri`'s stop lift its pause, and an owner's pause after it stays
- root-owned DB journal files left by an interrupted Fri phase, recovered by rollback
- a crash right after the pause commits
- a resume repeated after an interrupted result write and after a complete one, and refused for a different result
- cleanup pruning older release images while keeping this release's, non-release tags and an image a container uses
- cleanup keeping the previous release's rollback images and, when repeated after a newer release went live, that release's pinned images, including an idle worker's
- a rollback after resume retried with `BATCH_ATTEMPT=2`, for a Gene release and a Fri-only one, through resume and cleanup
- a second-day release from `7d6e36a` (marked source, features already there), whose rollback keeps profile removals and reply-check findings and removes only member summaries
- a Fri-only release that never touches Gene, then `rollback-fri` after resume, and `resume-old`
- a Fri-only release whose `rollback-fri` finds Gene moved by a member request, before it starts and during its fence: it refuses with Fri untouched and development running
- cleanup, repeated for a finished release while another is staged and drained, keeping every image of the unfinished one
- a Fri-only coordinator crash mid-switch, a retry that doesn't retake the backup, then `rollback-fri` and a repeat of it
- a third Fri release after a Fri-only release, which `rollback-fri` refuses without changes
- a Gene-only release that never touches Fri, then a rollback that leaves Fri alone

## After the release
- The owner can DM Fri "fri health" and should see the watch running, the controller up at G, and a fresh Gene heartbeat.
- Requests in review from before the release get stale notices, as after any deployment. Completing them needs a rebuild.
